# Nolane Agent 5.0.0-beta.6 — Checkpoint 14 Development Baseline

Nolane Agent is a local-first, evidence-driven agent workspace. It turns a user goal into governed missions, tasks, tool calls, verification, independent review, evidence and completion receipts while preserving human control.

This branch starts Checkpoint 14 — **Trust, Adoption & Autonomy** — from the verified Checkpoint 13 release commit `72f35b57aa32299bb4369eb84759c489b03ce697`.

## Product architecture

```text
Goal / conversation
→ mission plan and DAG
→ task workspace or worktree
→ AgentLoop and governed tools/providers
→ verification and independent review
→ evidence, receipts and completion gates
```

The desktop product consists of:

- an Electron shell with a sandboxed renderer and narrow preload bridge;
- a loopback-only local HTTP runtime and durable SQLite/file stores;
- provider, model, repository, browser, MCP, plugin, tool and evidence systems;
- a four-level progressive experience: Everyday, Workspace, Studio and Expert;
- a signed Windows update trust chain and recovery boundary.

`ui-v3` is the editable progressive UI source. `ui-dist` is generated by `npm run build:ui-v3`. The older `ui` tree remains an explicit recovery/compatibility surface until its retirement gates pass.

## Compatibility boundaries

NolaneNative runtime code and packages are absent from production paths. Historical attribution remains in `THIRD_PARTY_NOTICES.md`.

`vendor/forge-os` is **not** the current product identity, but it remains a packaged compatibility/authority substrate consumed through `ForgeOsBridge`. Nolane must not claim complete substrate retirement until replacement receipts and packaging tests pass. See `docs/COMPATIBILITY-SUBSTRATES.md`.

## Build and verification

```bash
npm test
npm run build:ui-v3
npm run verify:checkpoint-13-progressive-experience
npm run verify:checkpoint-14-foundation
```

Windows installer and signed update artifacts are produced by the tag-triggered GitHub Actions release workflow. `config/update.json` and the production update public key are generated during release preparation; packaging declarations do not make them normal source-controlled trust inputs.

## Evidence limits

Local Linux validation can prove source behavior, schema and security contracts, deterministic UI builds, clean-room packaging and portable artifacts. It does not by itself prove provider-real compatibility, local-model hardware performance, Windows GUI/accessibility behavior, Authenticode signing, successful NSIS relaunch, or no-data-loss update replay. Those claims require their own external receipts.
